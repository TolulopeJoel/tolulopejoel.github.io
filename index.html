Production AI

01

llm agents · permissions · in production at Schulltech

ApproveHR: AI Assistant

An assistant inside an HR and payroll platform that answers questions and takes actions on real employee records. The hard part was never the model. It is that the assistant must never show one employee another’s salary.

  • A permission-aware catalogue declares what may be queried, gated per field and scoped per row against the asking user’s own permissions.
  • Reads and writes are separate. An action carries a mandatory gate and an audit entry identical to the hand-driven route.
  • The confirm button’s label is read from the database, never written by the model, so the assistant cannot word its own confirmation.
  • Token spend is metered per organisation; every turn is traced, with verbosity levels because traces carry real pay figures.
TypeScript Prisma React Multi-provider LLM

02

text-to-sql · langgraph · evals · core engine

Kowane: Banking Ops Assistant

A text-to-SQL agent for microfinance banks. Ask “what is our exposure on overdue loans?” and get the answer with a chart, not a result set.

  • LangGraph workflow with schema documents retrieved from ChromaDB, and a validation layer sitting between the model and the database.
  • It ships with an eval harness, not just tests. Pytest tells you the code still does what it did yesterday, and nothing about whether the agent still answers correctly after a prompt edit or a model upgrade.
  • Real questions through the real graph: gold-SQL comparison, baseline regression detection, and repeat runs to catch flakiness.
  • Checkpoints are encrypted at rest. A LangGraph checkpoint carries the question, the SQL that ran and the rows it returned: the bank's own customer data. So it does not sit in plaintext on disk.
Python LangGraph ChromaDB Evals
kowane.com ↗

Direction

Where I'm going.

Measurable
systems

Most teams shipping an LLM feature can tell you their tests pass. Very few can tell you whether the thing is right, or whether last week's prompt edit made it worse. That gap is where I want to keep working: gold sets, regression baselines, and suites people actually trust enough to act on.

In flight: extending a text-to-SQL eval suite past 27 cases. The categories that earn their place are the ones testing what the agent should refuse.

Retrieval that
understands structure

Semantic search finds what a question mentions, not what it needs. The table that bridges two others is named in neither the question nor the results, and the model invents its columns: a class of bug that parses, executes and returns a plausible wrong number.

In flight: foreign-key graph expansion over retrieved schema · and rebuilding Scene Rec's matcher on embeddings across 7,656 films, measured as recall@k against the lexical baseline it replaces.

Agents that can't
do the wrong thing

A prompt instruction is a request. A permission is a boundary. I'd rather spend the effort making a wrong action impossible than making it unlikely: generating the tool surface from the caller's own rights, keeping the confirmation out of the model's hands, writing the same audit entry a human action would.

Looking for: more of this. It is the half of agent work that gets skipped until something goes wrong in front of a customer.

I want to build where being wrong costs something: finance, health, anything regulated. That's where you can't ship and see, and it's where the interesting problems are.
